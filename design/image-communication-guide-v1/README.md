# 后续图片沟通约定 · v1

2026-10-13，用户确认下面这种真实绝对路径链接可以打开图片，并明确要求“把这个作为之后我们沟通图片的方式，写进GitHub文档里”。本约定适用于本项目后续美术/UI对话交付图片。

## 必须使用的格式

用普通文字消息中的Markdown文件链接发送图片，目标是当前工作区内真实存在的图片绝对路径：

```markdown
[查看草地模块原图](/workspace/generated_images/exec-bbb3f6a5-2cb1-40d4-8925-c92a3a7bbb13.png)
```

上例是本次用户已确认能打开的真实文件。后续必须换成对应图片的实际路径，先核对文件存在；不能复制示例文件名冒充其他图片。仓库副本也可按实际路径发送，例如：

```markdown
[查看草地组装地图](/workspace/classroom-boardgame/design/modular-hd-pixel-map-kit-v5/previews/grass_seed17_16x9.png)
```

- 默认发送这种可点击文件链接，不只依赖生成时临时显示的图片、嵌入预览或工具输出。
- 链接使用`[清楚的图片名称](/真实绝对路径/实际文件名.png)`；不只写文件名，不使用占位路径，不把链接包在行内代码里。
- 图片刷新后消失时，重发已生成图片的真实绝对路径Markdown文件链接；不重新生成、不删除或覆盖原图。
- 一次可按清晰名称列出少量图片链接，文字说明与图片链接一起发送；不要以工具读取成功声称用户已经看到。
- 用户表示收不到消息时，先用纯文字沟通；用户要求发“1”等连通确认时，只回复指定文字。解释问题以用户截图/真实证据为准，不把文件加载失败直接归因于GitHub。

## 文件与存档边界

绝对路径链接是当前聊天工作区的文件访问方式，不是GitHub公共图片URL，也不保证环境更换后永远有效。GitHub保存原图副本、文档和恢复存档；不要为了重发链接重新制作已存在的图片。若当前工作区文件失效，先从已存档原图恢复到实际路径，核对后再发链接。

本次已确认一次成功打开，不承诺文件服务503时任何链接都必然可用。素材审批、原生接入与图片能否打开是独立状态。

本约定只更新沟通资料，不改App、规则或旧资产。恢复存档见ARCHIVE_INDEX.md。
